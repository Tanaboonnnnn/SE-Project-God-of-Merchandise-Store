# F-04 — Atomic checkout, Order snapshots and idempotency

**Status:** PROPOSED for peer approval; not implemented. **Traceability:** FR-07/09/10/11/17; BR-07/08/09/10/11/15/19/20/25; NFR-03/04/05; DEC-016/020/021/023..026/028/032; CR-ENG-001 B/C. **Dependencies:** F-01/02/03, signed quote, PostgreSQL. [Shared contract](README.md).

## Vertical workflow / UI

Customer reviews cart/address/pin + server fee, explicitly confirms current destination, frontend disables Submit while one attempt is pending and generates one UUIDv4 Idempotency-Key **per logical Order**. On uncertain timeout, retry **identical payload and key**; do not auto-generate a new key. Successful commit shows saved PENDING Order detail; validation/stock error keeps cart and fields for edits, clears stale quote/confirmation, no phantom receipt. Once Order exists its contents cannot be edited; to make a new Order after Cancel use a new key and new validation.

## API / request/response policy (proposed)

`POST /api/orders` Customer-only, authenticated+anti-CSRF, header `Idempotency-Key: UUIDv4`, JSON `{ "items":[{"optionId":"uuid","quantity":2}], "destination":{"recipientName":"Example", "phone":"0812345678", "addressLine":"...", "subdistrict":"...", "district":"...", "provinceId":1, "postalCode":"10140", "pin":{"latitude":13.65,"longitude":100.49}}, "destinationRevision":"uuid", "confirmedRevision":"uuid", "quoteToken":"opaque" }`. Client cannot set customerId/role/price/total/fee/status. First committed success: `201` + `Location: /api/orders/:id` with `{ "data":{"id":"uuid","status":"PENDING","subtotalSatang":...,"shippingFeeSatang":...,"totalSatang":...,"items":[...]}}`; replay same customer+key+canonical payload: `200` same Order ID/current persisted status, no inventory mutation; reused key with changed canonical payload: `409 IDEMPOTENCY_KEY_REUSED`; in-flight bounded wait: `409 CHECKOUT_IN_PROGRESS` with `Retry-After: 1` and same-key retry; quote stale/unconfirmed: `409 QUOTE_STALE`; stock shortage: `409 INSUFFICIENT_STOCK`; malformed quantity/schema: `422 VALIDATION_ERROR` with failing line indices; DB unavailable: safe 503, no phantom Order.

**Canonical fingerprint [PROPOSED]:** validate every raw line *before* grouping; quantity strictly JSON integer 1..10 per entry, reject negative, zero, fraction, numeric strings, invalid IDs. Sum duplicate **identical option IDs**, ensure aggregate 1..10 and current Available; sort option IDs lexically. Normalize recipient/address text trim + Unicode NFC, preserve phone/postcode leading zeros, use province ID, pin serialized to fixed 6 decimal digits (pending coordinate-rounding review); hash deterministic JSON structure of normalized items+full destination with SHA-256. Do not include client price/total/CSRF/quote token in fingerprint; compare fingerprint before interpreting a replay as new checkout. For an identical retry with a **committed key**, return original Order even if quote has since expired or Order has changed status: only the original committed request/payload is eligible for such replay.

## DB transaction/persistence contract

`Order(id, customerId FK, status=PENDING, immutable contact/address/provinceName/pin/distance/price snapshots, rejectionReason nullable)`; `OrderItem(orderId FK, optionId FK, quantity, unitPriceSatang, product/size snapshot, UNIQUE(orderId,optionId))`; `CheckoutAttempt(customerId FK, key UUIDv4, fingerprint, orderId FK, UNIQUE(customerId,key))`; Inventory for exact option maintains nonnegative Available/Reserved/Sold. Backend reads authoritative prices and recalculates fee in the transaction, starts `READ COMMITTED` transaction, acquires key uniqueness, applies sorted per-option guarded `UPDATE Inventory SET available=available-q, reserved=reserved+q WHERE option_id=id AND available>=q`, requires exactly one row each, creates Order, normalized OrderItems and key mapping and commits **together**. Failed item, exception or deadlock rolls back *every* write including key claim. No separately committed in-flight placeholder. Two Customers racing for last unit can never both commit; duplicates under same Customer+key cannot both reserve. Retry **entire transaction** only for SQLSTATE `40P01`/`40001` (proposed max 3 attempts with capped delay), preserving idempotency key. Unique key is durable for Sprint 1 while Order retained; no automatic expiry/TTL. Exact lock timeout, scope and retry parameters require real DB tests and peer approval.
