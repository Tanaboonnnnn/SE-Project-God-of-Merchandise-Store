## Shipping tariff implementation notes (DEC-007)

**Decision status: confirmed tariff, not yet an approved implementation spec.** The band boundaries below apply to the straight-line distance selected by the customer (DEC-006), with the dispatch origin at KMUTT Bangmod (DEC-005; exact coordinates pending).

| Distance from dispatch point | Shipping fee (per order) |
| --- | ---: |
| `0 <= d <= 50 km` | 40 THB |
| `50 < d <= 300 km` | 80 THB |
| `d > 300 km` | 150 THB |

Boundary examples to turn into tests under DEC-011: exactly 50 km → 40 THB; 50.04 km → 80 THB even if displayed as 50.0 km; exactly 300 km → 80 THB; 300.001 km → 150 THB. Never use a display-rounded distance to select the fee band. Invalid, missing or out-of-range destination coordinates must not yield a trusted shipping total. The backend must recalculate order totals; client-submitted fees and totals are not authoritative. Distances are **straight-line** estimates, not actual road distances or real carrier quotes.

**Implementation sprint: Sprint 1, confirmed in DEC-008.** DEC-011 resolves fractional-distance handling: select the tariff band using the computed distance before display rounding (no rounding to nearest kilometer or 0.1 kilometer for fee selection). Still open: display formatting; verified coordinates for the DEC-010 simulated campus-center dispatch point; and backend failure behavior not covered by DEC-029. ## DEC-016 inventory reservation and acceptance (confirmed)

## DEC-017 Operator rejection and reservation release (confirmed)

- **Allowed action in Sprint 1:** an authenticated Operator can reject an order that was submitted but has not been accepted or previously rejected. The rejected order retains its persisted order history/status; it does not become an accepted sale.
- **Inventory effect:** for every order line, move the quantity reserved for that order back into the available stock of the **same sellable option** (including the exact T-shirt design and size), immediately on successful rejection. The release occurs **once only**; retries or duplicate requests must never add stock again.
- **Workflow boundary:** Operator Accept converts reserved units to sold; Operator Reject returns them to available. An already accepted order **cannot be rejected** with this action. **DEC-033 additionally requires the Operator to supply a non-blank rejection reason, saved with the Rejected Order and visible only to the owning Customer and Operators; invalid/missing reasons must cause no stock/status change.** DEC-018 permits a Customer to cancel only their own **Pending** order and return its reservation. DEC-019 prohibits cancellation after acceptance in Sprint 1; any later-sprint cancellation and returns policy remains undecided.
- **No automatic expiry:** pending reservations stay reserved until a successful Operator Accept/Reject or the owning Customer cancels while the order is Pending. Do not implement an automatic 24-hour timer or infer an expiry policy.
- **Engineering contracts/test cases (implementation implications):** perform the rejection status update, **required rejection-reason persistence**, and stock release together (all order lines or none); require Operator authorization; reject illegal status transitions and missing/whitespace-only reasons without any state or inventory change; test duplicate Reject, Reject after Accept, Accept after Reject, competing Accept-vs-Reject requests, and owner-only Customer visibility of the reason (while all Operators can view it). The exact API response to repeated requests and transaction implementation are still open.

## DEC-018 Customer cancellation of Pending orders (confirmed)

Cancellation does not move anything to Sold. This mirrors the reservation release on Operator rejection (DEC-017), but the authorized actor and final order status differ.

## DEC-023 per-option order quantity cap (confirmed)

- **Rule:** each exact sellable option in a submitted Sprint 1 order must have an **aggregate requested quantity of 1–10 whole units**, and that quantity must not exceed its **current Available Stock** (DEC-016). - **Duplicate-line case:** if the request contains multiple entries for the **same exact option**, add their quantities **before validating the cap**. For example, notebook quantities 6 and 5 count as 11 notebooks and cannot pass validation; splitting a request into duplicate lines does not bypass the cap. Under DEC-025, valid repeated entries for one option become a single persisted Order Item with their summed quantity; no silent change in ordered quantity is permitted.
- **Variant case:** T-shirt design A size S and design A size M are two different sellable options; the 1–10 cap and Available Stock checks apply independently to each. The same design-and-size repeated within an order is one option for quantity-cap enforcement.
- **Server and test contract:** reject zero, negative, fractional, non-numeric or over-cap quantities and reject quantities above available stock; do not trust client-side validation. Cover the boundaries 1, 10 and 11, duplicate entries adding to 10 versus 11, size-specific independence, and stock-constrained quantities. Preserve DEC-016 atomic reservation and DEC-017/018 exactly-once release behavior.
- **Resolved by DEC-024:** any invalid or unavailable line causes the entire order submission to fail with no persisted Order or stock reservation; the Customer corrects the request and resubmits. **Still open:** any additional cross-option total-order cap. DEC-025 now confirms the one-Order-Item-per-option persisted representation.

## DEC-024 all-or-nothing order submission (confirmed)

- **Trigger:** if any line in a multi-line or single-line submission fails server-side validation (e.g., insufficient Available Stock for a specific size, zero/fractional/negative quantity, or an aggregate duplicate-option quantity exceeding 10 under DEC-023), the **entire submission fails**.
- **No partial effects:** create/persist **no Order** and allocate/reserve **zero units across every requested option**. Validation and stock reservation must be completed atomically against current inventory; a partial or orphaned reservation is not an acceptable outcome. This extends DEC-016's reservation guarantee and does not authorize partial fulfillment.
- **Customer feedback:** identify the invalid/unavailable line(s) and allow the Customer to revise their request and explicitly submit again. Do **not** silently reduce quantity, discard an item, adjust the order total, or submit a revised basket without the Customer's new action.
- **Vocabulary boundary:** a failed **order submission** produces no persisted Order and no **Rejected** order status. An **Operator-Rejected Order** under DEC-017 was previously created successfully, reserved inventory, then had its reservation released upon Operator rejection. Do not conflate these two failures.
- **Verification scenarios:** T-shirt A/M requested 2 with Available Stock 1 alongside an available notebook => neither line is reserved and no Order is created. A duplicate option with quantities 6 and 5 => full rejection at the DEC-023 cap. A database/transaction failure during submission => no persisted Order or reservation side effects. A corrected, newly submitted valid request may succeed; concurrent submissions cannot oversell.
- **Still open:** exact API error code/response shape, and any aggregate total-item cap. DEC-025 confirms normalization of valid duplicate entries into one persisted Order Item per sellable option. Implementation specifics belong in the Sprint 1 Engineering Contract.

## DEC-025 duplicate sellable-option entries (confirmed)

- **Normalized persisted line:** a successfully submitted request has **at most one Order Item per exact Sellable Option**. Multiple valid request entries for the same option are combined by summing their quantities before persistence; e.g., notebook x3 + notebook x2 becomes one notebook Order Item with quantity 5 and a product-line subtotal of `5 x 70 THB = 350 THB` (before order-level shipping).
- **Distinct options stay distinct:** T-shirt A/M and T-shirt A/L are separate Order Items even though they share the T-shirt A design-level unit price. Different product designs or standalone products also remain separate.
- **Validation and atomicity:** check that **each raw entry** has a valid positive whole-number quantity; sum per exact option and check the combined DEC-023 cap (`1 <= quantity <= 10`) and current Available Stock. A negative or fractional raw entry must not be masked by a valid total. If any entry or aggregate is invalid, DEC-024 rejects the entire submission with no Order or reservation. A valid request persists one Order Item and reserves exactly the combined quantity per option, atomically under DEC-016.
- **Pricing:** derive authoritative unit price server-side and record the Order Item price snapshot; quantity aggregation never changes the price for an option and never allows user-submitted totals to override backend calculations.
- **Test examples:** notebook x3 + x2 -> one persisted notebook line, quantity 5, subtotal 350 THB; notebook x6 + x5 -> whole-request rejection, no order or reservation (DEC-023/024); T-shirt A/M x2 and A/L x1 -> two different items and independent size reservations; a malformed duplicate entry -> whole-request rejection.
- **Still open:** the API response schema and an optional overall distinct-options cap. **DEC-026 now resolves duplicate whole-order submissions** with Backend Idempotency Keys and Frontend click prevention; it is distinct from duplicate product lines within an order. Precise retry response and mismatch behavior remain for the Engineering Contract.

## DEC-026 repeat whole-order submissions and Idempotency Keys (confirmed)

- **Business intent:** one customer checkout submission should produce at most one persisted Order and one set of inventory reservations, even if the same request is retried because of a double-click, slow connection, timeout or concurrent delivery of the same logical attempt. This is separate from DEC-025 duplicate line aggregation.
- **Frontend guard:** disable/prevent repeated Submit actions while the checkout request is pending. This guard alone is insufficient because API requests can be retried or duplicated outside the UI.
- **Backend authority:** require an Idempotency Key that identifies the logical submission. Replays of that submission return the earlier order/result and cause no additional order creation, price calculation side effects or Reserved Stock allocation. New intentional checkouts use **new keys**, even when basket contents are identical. Keep ownership/authorization checks from DEC-012 in force on replayed responses.
- **Concurrency / atomicity:** the backend must prevent two overlapping attempts with the same key from each committing a separate Order/reservation. DEC-016 and DEC-024 still require atomic full-order creation/reservation and no partial side effects.
- **Test cases:** two immediate identical requests with one key -> one Order and one reservation; retry after a successful response was lost -> original Order/result, no second reservation; a new key for a new deliberate checkout -> independent order if stock and all validations pass; concurrent same-key submissions -> at most one committed Order. Also test attempts to retrieve an order belonging to another customer via key reuse.
- **Contract details not yet decided:** scope/storage of keys, key lifetime and expiry, whether a reused key with changed payload returns a conflict, response code/shape during in-flight submissions, and retries after failed validation. Do not infer those specifics from DEC-026; design securely in the Sprint 1 Engineering Contract.
- **Design tree:** DEC-016 atomic stock reservations + DEC-024 all-or-nothing order creation + DEC-025 normalized items -> DEC-026 idempotent whole-order submission (confirmed) -> engineering contract for replay/concurrency semantics (open). DEC-027 now confirms shared single-store Operator visibility and Pending-only Accept/Reject rights.

- **Interaction with DEC-029:** if the map later fails to load, the previously selected pin must also be explicitly reconfirmed as required by DEC-029. - **Verification examples:** with no explicit acknowledgement, do not submit the Order; with acknowledgement and otherwise valid data, continue with the existing backend checks; changing the pin or address after acknowledgement must not silently retain outdated consent (define precise UI invalidation mechanics in the Engineering Contract); a pin in an inconsistent province is **not** automatically detected by this rule.
- **Design tree:** DEC-003 nationwide delivery + DEC-006/013 selected pin and structured address + DEC-029 map failure handling -> DEC-030 explicit Customer address/pin confirmation (confirmed) -> DEC-031 address-field validation policy (confirmed) -> DEC-032 post-submission order immutability (confirmed). The separate Operator rejection branch is DEC-016/017/027 -> DEC-033 mandatory rejection reason (confirmed).

## DEC-031 recipient and structured delivery-address validation (confirmed)

- **Required fields:** recipient name, contact phone, house/street or address detail, subdistrict, district, province and postal code (DEC-013), plus the mandatory selected map pin. A blank/whitespace-only recipient name or any required address text field is invalid. The Customer must still confirm the displayed address and pin under DEC-030.
- **Basic syntax checks:** the mobile-number value must be exactly 10 digits, first digit `0`; the postal code must be exactly 5 digits. The province is selected from a fixed Thai-province list; district and subdistrict remain typed text. The Backend must enforce these rules irrespective of Frontend validation; do not silently repair malformed contact or postal values.
- **No proof of geographic consistency:** do not automatically validate that the province, postal code, district, subdistrict or selected map pin correspond. A syntactically valid Thai province and postal code may still describe different places. A valid pin remains necessary for shipping computation (DEC-006/029), but it does not prove the entered address is accurate.
- **Suggested boundary tests:** `123` as a mobile number fails; 10 digits not beginning with `0` fail; exactly 10 digits beginning with `0` pass this basic format rule. `ABC12`, four digits and six digits fail postal-code syntax; five digits pass syntax without geographic verification. Blank/whitespace fields and unlisted province values fail. Check Backend directly as well as through the form; invalid checkout creates no Order or inventory reservation (DEC-024).
- **Still open in Engineering Contract:** accepted digit character set, refined mobile-prefix rules, exact field lengths, allowed characters, fixed Thai-province dataset/source, error responses and display semantics. DEC-031 does not approve online address lookup or automatic address-to-pin matching.
- **Design tree:** DEC-013 structured delivery address + DEC-029 map failure + DEC-030 mandatory address/pin acknowledgement -> DEC-031 basic validation (confirmed) -> DEC-032 no edits after successful submission (confirmed).

## DEC-032 submitted-order contents are immutable in Sprint 1 (confirmed)

- **After successful submission:** The persisted Order has fixed sellable options, quantities, recorded unit-price snapshots, recipient name/phone, structured delivery address and selected destination pin. Do not offer a Customer-side edit of these values while the Order is Pending, Accepted, Rejected or Cancelled. The server-authoritative subtotal, shipping fee and total recorded at submission are not silently revised by a Customer edit. This does not forbid authorized Order Status changes.
- **To correct a Pending Order:** Only its owning Customer may first **Cancel** it (DEC-018), releasing that order's reservations **atomically and exactly once**, and then **place a new, distinct checkout** with a new Idempotency Key (DEC-026). A new Order is not an in-place amendment of the old one. It must be independently validated against current catalog prices, availability and quantity limits, recipient/address rules, address-and-pin acknowledgement and backend-computed shipping fee; its price or availability need not match the cancelled Order.
- **After acceptance:** Customer cannot edit or cancel an Accepted Order during Sprint 1 (DEC-019). Rejected and Cancelled Orders likewise cannot have their content changed. No post-acceptance return, refund or editable-order flow is authorized by this decision.
- **Authorization/concurrency:** A Customer cannot edit another Customer's Order and cannot cancel a non-Pending Order. Concurrent Operator Accept/Reject and Customer Cancel must still produce one legal transition and one correct stock movement (DEC-016/017/018/027), not a content edit or duplicate reservation.
- **Suggested tests:** request to update a Pending Order's quantity, size, address or pin is rejected with persisted values unchanged; own Pending cancellation releases each reservation once; new checkout uses new key and may succeed or fail independently; Accepted/Rejected/Cancelled content edit attempts are rejected; Customer B cannot cancel Customer A's Order; replaying an old checkout key does not create an additional Order (DEC-026).
- **Design tree:** DEC-016/018/019 (reservations and eligibility to cancel) + DEC-023/024/025 (order-line validity) + DEC-026 (new submission identity) + DEC-030/031 (destination confirmation and address validation) -> DEC-032 immutable submitted Order (confirmed). Operator rejection explanation is separately resolved in DEC-033.

## DEC-033 Operator rejection reason and visibility (confirmed)

- **Who and when:** An authenticated Operator (any account with the Operator role under DEC-027) may Reject **only a Pending Order**. Before a Reject can succeed, that Operator must provide a rejection reason with non-whitespace content; a missing, empty or whitespace-only reason is invalid. Whether to impose a maximum length and the exact UX/API validation messages are Engineering Contract details, not additional team-approved business values.
- **Recorded explanation:** On successful Reject, persist the rejection reason on the same existing Order as its **Rejected** status. It explains the Operator's decision, is not a change to the immutable Customer-submitted items/address/prices from DEC-032, and is distinct from an invalid checkout submission under DEC-024 (which never creates an Order).
- **Authorization and privacy:** The owning Customer may read the reason for their own Rejected Order, and authenticated Operators may read the reason for any Campus Store Rejected Order. Other Customers cannot access it through list, detail, direct API access or identifiers of someone else's order. The reason is customer-visible text, not a private internal Operator note; the Operator-facing UI should make that visibility clear. A Customer cannot set or edit this reason.
- **Atomicity/inventory:** The transition Pending -> Rejected, saving the reason, and releasing every related Reserved Stock quantity to Available are **one atomic operation**. If validation/authorization/transition/persistence fails, perform **no** status change or stock release. A successful Reject releases stock **once**; duplicate Reject, Reject after Accept/Cancel, and races with Accept or Customer Cancel must not alter the final reason or repeat a release.
- **Verification examples:** a blank/whitespace-only reason does not reject or release inventory; a valid reason persists along with Rejected status and exactly-once release; the order owner can view it but another Customer cannot; any Operator can view it; invalid status/racing requests do not leave stock/reason inconsistencies. Define response codes, message-length limits and database transaction mechanics later.
- **Design tree:** DEC-016 reserved stock -> DEC-017 Pending-only Operator Reject + stock release -> DEC-027 shared Operator authority -> DEC-033 mandatory reason + restricted visibility + atomic Reject (confirmed). DEC-034 now confirms owner-only status lookup via My Orders/Order Detail without proactive notifications in Sprint 1.

## DEC-034 Customer Order Status lookup without proactive notifications (confirmed)

- **Customer-facing read:** An authenticated Customer can see their own persisted Orders in **My Orders** and open an **Order Detail** for each owned Order. Display the latest recorded **Pending, Accepted, Rejected or Cancelled** status when the view is opened or refreshed. For a Rejected Order, show its recorded Operator rejection reason to the **owning Customer** (DEC-033). The data must come from the backend's persisted order record rather than a frontend-only assumed transition.
- **Authorization boundary:** A Customer cannot list, fetch, infer or view another Customer's Order Status, detail or rejection reason. The restriction must be enforced by the backend, including direct API requests, not merely by hiding UI links. Any Operator may view all Campus Store orders under DEC-027.
- **No proactive channel in Sprint 1:** No email, push message, SMS, notification badge/inbox, websocket/realtime status alerts or other automatic status-change notification is required or approved. A Customer must visit or refresh the relevant view to discover a change. Ordinary form/submission feedback is not an order-status notification system.
- **Verification candidates:** owner sees the current persisted Order Status after an Operator Accept, Reject or eligible Customer Cancel and a refresh; the owner sees a saved reason for Rejected; another Customer receives no private data via list or direct detail lookup; the UI does not rely on stale local state as the authority. Define API/refresh behavior and error/loading states in the Sprint 1 feature contracts.
- **Design tree:** DEC-012 account/ownership + DEC-017/018/019 Order lifecycle + DEC-027 Operator scope + DEC-033 rejection reason -> DEC-034 Customer-initiated status lookup (confirmed). There is no remaining undecided Sprint 1 notification-channel requirement.
